Wallet API

Una billetera digital donde el dinero nunca se crea ni se pierde.

API REST en la que los clientes abren cuentas en pesos chilenos, depositan, retiran y se transfieren dinero simulado. Cada movimiento queda en un libro contable de doble entrada, y el sistema se mantiene consistente aunque lleguen cientos de operaciones a la vez o un cliente repita una petición.

El objetivo

Un sistema que mueve dinero tiene una sola obligación que no admite excepciones: el saldo siempre tiene que ser correcto. Que una operación falle a la mitad, que dos transferencias lleguen al mismo tiempo sobre la misma cuenta o que un cliente reintente una petición por un timeout no puede crear ni hacer desaparecer dinero.

Este proyecto resuelve esos problemas con las herramientas que se usan en sistemas financieros reales, y demuestra con pruebas que funcionan. Es un proyecto personal de portafolio: la calidad y la corrección importan más que la cantidad de funciones.

Lo interesante por dentro

  1. El saldo no se guarda: se calcula

    Ninguna tabla tiene una columna de saldo. Cada operación genera asientos de débito y crédito que suman lo mismo, y el saldo es la suma de los asientos de la cuenta. No existe un dato que pueda quedar desincronizado, y una conciliación verifica en cualquier momento que el libro cuadra.

  2. Bloqueos en orden fijo contra los deadlocks

    Antes de validar un saldo, las cuentas se bloquean con SELECT ... FOR UPDATE, siempre en el mismo orden. Si A transfiere a B mientras B transfiere a A, ambas operaciones esperan por la misma cuenta en lugar de bloquearse entre sí.

  3. Una petición repetida no mueve el dinero dos veces

    Depósitos, retiros y transferencias exigen una clave de idempotencia. Una repetición recibe exactamente la respuesta original, y las peticiones simultáneas con la misma clave se ordenan con un advisory lock de PostgreSQL.

  4. La base de datos no confía ciegamente en el código

    Triggers impiden modificar o borrar asientos, y un trigger diferido verifica al confirmar cada transacción que sus asientos cuadren. Un error en la aplicación no puede dejar el libro descuadrado.

  5. Pruebas que se comprobó que detectan errores

    Cien hilos simultáneos atacan las mismas cuentas a través de HTTP. Para confirmar que esas pruebas sirven, se rompió el código a propósito. Sin el bloqueo fallan tres de cuatro escenarios; con el orden de bloqueo invertido PostgreSQL detecta deadlocks.

  6. Ninguna entrada provoca un error interno

    Más de sesenta casos de entradas inesperadas, entre ellos caracteres de control, JSON roto, números que desbordan, intentos de inyección SQL y rutas para evadir controles. Ninguno responde 500, y cada error trae un código estable y su motivo.

Seguridad

Sesiones que detectan robos

Los refresh tokens se guardan como hash y se rotan en cada uso. Si alguien reutiliza uno ya usado, se cierran todas las sesiones del usuario.

Sin pistas para un atacante

El inicio de sesión responde igual y tarda lo mismo exista o no el correo, y las cuentas ajenas responden como inexistentes.

Revisado en cada cambio

CodeQL analiza el código en cada push y Dependabot vigila las dependencias. Hay pruebas que intentan usar tokens falsificados y sin firma.
